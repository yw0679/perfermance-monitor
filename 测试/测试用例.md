# 最终目标
| 环节 | 正常场景 | 异常或边界场景 |
|---|---|---|
| 启动配置 | 使用 1 秒、3 秒间隔启动 | `0`、负数、`abc`、超大整数 |
| 采集 | worker 持续产生采集输出 | 所需设备或权限不可用 |
| 上报 | manager 正常接收样本 | manager 地址不可达 |
| 存储 | 本轮样本写入数据库 | 数据库不可用 |
| 退出 | 收到 SIGINT 后正常退出 | 退出等待超时、进程残留 |

| 字段 | 内容 |
|---|---|
| 编号 | START-001 |
| 测试目的 | 检查 worker 能否正常启动并进入采集流程 |
| 前置条件 | 已构建 worker；必要内核模块、权限和运行依赖就绪；manager 正常运行 |
| 输入 | manager 地址 `127.0.0.1:50051`，间隔 `1` 秒 |
| 操作 | 启动 worker，观察进程和日志，检查结束后发送 SIGINT |
| 预期结果 | 在规定时间内出现初始化及采集日志；观察期间进程持续运行；收到 SIGINT 后正常退出 |
| 执行证据 | 本轮日志、退出码、pytest 执行结果 |


短时间中断，缓存未满时恢复。
| 阶段 | 操作 | 主要检查 |
|---|---|---|
| 正常 | worker 向测试 manager 上报 | 正常采集，没有连接失败 |
| 中断 | 停止测试 manager，worker 保持运行 | 上报失败，出现缓存重试日志 |
| 恢复 | 重新启动测试 manager | 出现补传成功日志，恢复正常上报 |
| 数据核对 | 查询本轮 sequence | 检查中断期间的样本是否补入数据库 |

5.
先从 worker 的启动和参数处理入手，基于已有脚本补充了 pytest 用例。
用例包括正常的 1 秒、3 秒间隔，以及 0、负数和 abc。
其中，0 和负数按照当前约定应该回退到 1 秒，
abc 应该被拒绝，并返回明确的错误信息。
自动化方面，我用 fixture 管理 worker 启动和退出，
每轮保存独立日志，通过进程状态和日志检查启动、配置处理及采集流程。
对于非法输入，则用 subprocess.run 获取退出码和错误输出。
测试中发现，传入 abc 时，std::stoi 抛出的异常没有被捕获，
导致程序异常终止，退出码是 -6。定位后补充了参数转换的异常处理，
让程序输出错误提示并返回错误码 1。
修复后，我先重跑失败用例确认问题解决，再执行已有用例检查影响，
最终这 5 个测试项全部通过。

6.
我使用 iperf3 构造正向和反向 TCP 流量，检查流量开始、持续和结束时的采集表现。
正向测试中发送速率明显上升，反向测试中接收速率明显上升；
大流量期间，进程级统计能够识别到 iperf3 及其 PID，结束后流量回落。
再统一单位，核对吞吐量的数量级，结果符合预期。

7.
我做过 manager 中断与恢复测试。先正常上报，再停止 manager，保持 worker 运行，观察上报失败、缓存积压和重试行为。恢复 manager 后，日志显示 19 条缓存样本补传成功。我进一步根据主机标识和 sequence 查询数据库，确认这 19 条样本全部入库，本轮总共 34 条样本也没有缺失或重复，形成了日志和数据库两方面的验证证据。
